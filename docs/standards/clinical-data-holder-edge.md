# Synthetic HIE/EHR clinical-data holder edge

Evidence status: **`executed_local` — Executed local**.

This bounded adapter demonstrates how CareTrust delegation and trust context
could accompany a request from an authorized participating organization's
application and user to a health information exchange or EHR without making
CareTrust the clinical-data authority. The caregiver is the delegated subject
in the context; the caregiver is not the HIE requester, authorized user, or
clinical-data recipient. The implementation and all examples are synthetic,
execute without a network call, and use the reserved
`https://ehr.synthetic.invalid` endpoint.

No Hawaii Health Information Exchange system, participant, endpoint, data,
patient-matching service, policy, or endorsement is represented. “HIE/EHR” in
this document names an architectural role only.

## Authority boundary

| Question | Authority in this edge |
| --- | --- |
| Is there an active CareTrust relationship/delegation context? | CareTrust supplies bounded context |
| Does that context establish legal authority? | No; `legal_authority_status` is fixed to `not_established` |
| Is the organization an eligible participant, is its client registered, and is its user authorized? | The data holder |
| Which local patient, if any, matches the opaque patient hint? | The data holder |
| May this request disclose clinical data under local law, policy, consent, identity, and security controls? | The data holder |
| Which FHIR resources and scopes are returned? | The data holder, bounded by both delegation scope and local policy |

The request identifies `participant_org_ref`, `client_id`, and
`authorized_user_ref`; fixes `requesting_actor_role` to
`authorized_participant_user`; fixes `clinical_data_recipient` to
`authorized_participant_application`; and fixes
`caregiver_is_requesting_actor` to `false`. The decision fixes
`requesting_party_eligibility_authority`, `patient_match_authority`, and
`disclosure_policy_authority` to `data_holder`.

A CareTrust context can narrow a request or cause a denial. It cannot make the
caregiver an HIE participant, authorize an organization/user/client, force a
patient match, or force a disclosure permit.

## Executed synthetic sequence

```text
authorized participating-organization user + registered client
  -> request carrying CareTrust caregiver delegation/trust context
  -> synthetic data holder
       1. verify participant eligibility
       2. verify client registration for that participant
       3. verify authorized-user eligibility for that participant
       4. reject revoked, inactive, or expired CareTrust context
       5. perform its own opaque patient match
       6. enforce delegation scope
       7. enforce independent local disclosure policy
       8. return a bounded synthetic FHIR bundle only to the participant app
```

`SyntheticClinicalDataHolderAdapter` in
[`src/caretrust/clinical_edge.py`](../../src/caretrust/clinical_edge.py)
executes this order deterministically. The complete exchange record links the
request, patient-match result, final decision, and optional FHIR bundle.
Unknown properties are rejected by strict Pydantic contracts.

## Retained examples

All five examples are generated by
[`scripts/export_clinical_edge_examples.py`](../../scripts/export_clinical_edge_examples.py)
and asserted byte-for-object against executed adapter output:

| Example | Patient match | Final decision | Returned data |
| --- | --- | --- | --- |
| [`permit.json`](examples/clinical-edge/permit.json) | `matched` by data holder | `permit` / `DATA_HOLDER_POLICY_SATISFIED` | One synthetic `CarePlan` in a collection `Bundle` |
| [`deny-unregistered-client.json`](examples/clinical-edge/deny-unregistered-client.json) | `not_attempted` | `deny` / `CLIENT_NOT_REGISTERED` | None |
| [`deny-no-patient-match.json`](examples/clinical-edge/deny-no-patient-match.json) | `no_match` | `deny` / `PATIENT_NO_MATCH` | None |
| [`deny-insufficient-scope.json`](examples/clinical-edge/deny-insufficient-scope.json) | `matched` | `deny` / `INSUFFICIENT_DELEGATED_SCOPE` | None |
| [`deny-revoked-fresh-request.json`](examples/clinical-edge/deny-revoked-fresh-request.json) | `not_attempted` | `deny` / `CARETRUST_CONTEXT_REVOKED` | None |

The revoked example is a distinct fresh request linked to the earlier request
ID. It does not rewrite a historical permit or claim that an existing session
was terminated.

The adapter also tests `PARTICIPANT_NOT_ELIGIBLE` and
`AUTHORIZED_USER_NOT_ELIGIBLE`. All three requesting-party failures stop
before patient matching.

## FHIR and authorization boundary

The permit payload is a strict local subset of a FHIR R4-shaped `Bundle` and
`CarePlan`. It contains no patient name, address, contact information,
identifier, diagnosis, encounter, medication, laboratory result, or real
clinical fact. The local patient reference remains inside the data-holder
response and match inputs are explicitly not disclosed to CareTrust. The
returned bundle's recipient is the authorized participant application, never
the caregiver directly.

The strings such as `patient/CarePlan.rs` are synthetic scope-shaped contract
values. This edge does **not** implement SMART App Launch, OAuth, UDAP, TEFCA,
FHIR REST, a FHIR validator, a consent resource, an MPI, identity proofing, or
an independent interoperability test. Production deployment would require all
applicable data-holder patient matching, consent, minimum-necessary, identity,
security, audit, legal, and disclosure controls.
